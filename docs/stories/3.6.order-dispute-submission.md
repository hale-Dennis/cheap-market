## Story
**As a** Buyer,
**I want** a way to report a problem with a completed order,
**so that** I can resolve issues with quality or accuracy.

## Acceptance Criteria
1. On the detail page for a "Completed" order, the buyer has a "Report Issue" button.
2. Clicking the button opens a simple form where the buyer can describe the problem.
3. Upon submission, the order's status is changed to "Disputed," and a notification is sent to the System Admin for review.

## Dev Agent Record

### Implementation Notes
- **`POST /disputes`** (existed; reworked) takes `{ orderId, reason }`. It records an `OPEN` dispute, sets the order to `DISPUTED` and writes an admin notification, all in **one transaction** (AC3).
  - The order row is locked first, so a simultaneous second report waits and then gets the 409.
  - The unique `order_id` constraint is also mapped to 409, as a backstop.
- **Errors:**
  - Another buyer's order returns **404**, as `GET /orders/{id}` does. It was 422 before.
  - An order that isn't completed returns **422 `ORDER_NOT_COMPLETED`**.
  - A repeat returns **409 `ALREADY_DISPUTED`**.
  - A blank reason, or one over 500 characters, returns **400** (bean validation).
- **Admin notification (AC3):** a new `DISPUTE_OPENED` type is written through `AdminNotifier`, the same mechanism as new orders in 3.3.
  - Message format: `Issue reported on order CM-… by {buyer}: "{reason}"`, with the reason shortened to 200 characters.
  - The dashboard panel marks these with a red "Dispute" tag.
- **Order page:**
  - `GET /orders/{id}` now includes `dispute` (status, reason, date) or `null`.
  - A completed order without a report shows **"Problem with this order?" with a "Report issue" button** (AC1).
  - Once reported, the page shows **"Issue reported"**: the reason, the date and the review state (open, under review, resolved). The status badge reads **Disputed** here and on My orders.
- **`DisputeFormModal`** (AC2):
  - a textarea labelled "What went wrong?" with the placeholder "Describe the issue";
  - an `n/500 characters` counter, and the field can't go over 500 (pasted text included);
  - Submit is disabled while the text is empty or only spaces;
  - a 409 shows a toast and refreshes to the existing report.
- **Ratings on disputed orders (decision, change to 3.5):** a disputed order was still delivered, so its farmers can still be rated. A buyer with a complaint is often exactly the one who wants to leave a rating. Previously a dispute would have hidden the Rate buttons and the ratings already given. `POST /ratings` and `farmersToRate` now accept `COMPLETED` and `DISPUTED`.
- **Deviations:**
  - A reason over 500 characters returns 400, not 422 `COMMENT_TOO_LONG`, following the project decision in 1.5 to keep validation errors at 400.
  - The files follow the codebase layout (`components/disputes/`, `services/disputeService.ts`).
- **Schema fixes:**
  - `reason` and `resolution_notes` were `@Lob`, which Postgres stores as large objects (`oid`). They are now `varchar(500)` and `varchar(1000)`.
  - The `notifications.type` check constraint generated for the old enum allowed only `NEW_ORDER`.
  - `ddl-auto: update` can't apply either change to existing tables. Locally, the `disputes` table (empty) was dropped and recreated, and `notifications_type_check` was dropped. CI starts from a fresh database.
  - **Any other existing database needs the same before deploying.** Putting migrations under a tool such as Flyway would avoid these one-off steps, and it's worth considering as its own story.
- **Test reliability:** the admin dashboard shows the 20 most recent notifications. The order-history infinite-scroll test placed 25 real orders, which could push another spec's notification out of view. That test now seeds its orders with a stub-only `POST /__test/orders` that creates no notifications.
- **Not in scope:** reviewing and resolving disputes, and what happens to the order afterwards, is the future admin story. The existing `/admin/disputes` endpoints are unchanged. The admin order-status endpoint still lets an admin move a disputed order to another status.
