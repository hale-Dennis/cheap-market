## Story
**As a** System Admin,
**I want** to create a new produce listing on behalf of a farmer,
**so that** their goods can be made available for sale on the platform.

## Acceptance Criteria
1. From the admin dashboard, an admin can initiate a "Create New Listing" workflow.
2. The creation form allows the admin to select a registered farmer from a list.
3. The form allows the admin to assign the listing to a category from the list created in Story 2.1.
4. The form must capture the produce name, a brief description, price, unit of measure (e.g., "per kg," "per bunch"), and the harvest date.
5. The admin must be able to upload at least one image for the produce listing.
6. Upon submission, the new listing is saved and associated with the selected farmer.

```json
{
  "farmerId": "f123",
  "categoryId": "c456",
  "name": "Organic Tomatoes",
  "description": "Fresh organic tomatoes grown without pesticides.",
  "priceCents": 1500,
  "unit": "per kg",
  "harvestDate": "2025-07-01",
  "imageUrls": [
    "https://res.cloudinary.com/demo/image/upload/tomatoes1.jpg"
  ]
}
```

Successful response (201):
```json
{
  "id": "p789",
  "farmerId": "f123",
  "categoryId": "c456",
  "name": "Organic Tomatoes",
  "priceCents": 1500,
  "unit": "per kg",
  "imageUrls": [ "..." ],
  "listingStatus": "ACTIVE",
  "createdAt": "2025-07-02T10:00:00Z"
}
```

### Technical Constraints
- Max 5 images per listing; images must be JPEG/PNG ≤ 2 MB.
- Price stored as integer cents to avoid floating rounding.
- Image URLs stored as array column or linked table.
- Reject more than 5 images with HTTP 422.
- Reject price ≤ 0 with HTTP 422.
- Allow only MIME types `image/jpeg`, `image/png`; invalid types return HTTP 422.

## Dev Agent Record

### Implementation Notes
- **Status codes (agreed with PO in 1.5):** price ≤ 0, more than 5 images and invalid image types return **400**, like all validation errors, not 422.
- **Image upload:** `POST /admin/uploads/images?farmerId=…` (multipart `files`, ADMIN) validates 1–5 files, ≤ 2 MB each, and JPEG/PNG **by file signature** (the client's Content-Type is not trusted), then stores them and returns their URLs. The form uploads first, then creates the listing with those URLs. `ImageUploadService` plays the role of the `ImageUploader` util in File Locations.
- **Storage (agreed with PO):** `ImageStorage` with two implementations chosen at start-up: `CloudinaryImageStorage` when `CLOUDINARY_URL` is set (folder `cheap-market/farmers/{farmerId}`), otherwise `LocalImageStorage` (files in `UPLOAD_DIR`, served at `/api/v1/media/{file}`; Docker keeps them in an `uploads` volume). **Production must set `CLOUDINARY_URL`** (Render's disk is not durable); `render.yaml` declares it.
- **Listing creation (endpoint existed):** `farmerId` must be a user with role FARMER; image URLs must have been issued by our storage; harvest date must be today or earlier (was wrongly `@FutureOrPresent`) and within the last year; name ≤ 100, description ≤ 1000, unit ≤ 30, price ≤ GH₵ 1,000,000; text is trimmed; listing defaults to `ACTIVE`. The response now includes description, harvest date and stock quantity.
- **Price:** the API takes `priceCents` (pesewas) and stores an exact `DECIMAL`; the form converts the typed cedi amount by string arithmetic (no floating point).
- **Form:** `/admin/listings/create` (dashboard → "Create new listing"): farmer (all farmers, with region) and category selects, name, description, price (GH₵), unit (preset list in shared-types), harvest date (date picker limited to the last year), and a photo picker with previews, removal and the 5 / 2 MB / JPEG-PNG limits. After saving, the form clears for the next listing but keeps the farmer selected.
- **Also fixed:** all forms now validate on submit and then re-validate as fields change. Validating on blur made errors appear mid-click, shifting the submit button so the click missed it (found by E2E).
- **Known limitation:** if creating the listing fails after the photos were uploaded, those photos stay in storage unused.
