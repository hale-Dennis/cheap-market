## Story
**As a** Buyer,
**I want** to place my order and receive a confirmation,
**so that** I know my purchase is complete and being processed.

## Acceptance Criteria
1. A "Place Order" button on the checkout page finalizes the transaction.
2. An order record is created in the database with a unique ID and a default status of "Pending".
3. The buyer is redirected to an "Order Confirmation" page showing the order details and order number.
4. A notification of the new order is sent to the System Admin.

## Dev Agent Record

### Implementation Notes
- **`POST /orders`** (existed; rewritten): turns the cart into a `PENDING`, `UNPAID` order at **current prices**, copies the delivery address (or links the pickup point), adds the region's delivery fee (`DeliveryFeeService`), empties the cart and notifies admins, all in one transaction. Errors carry codes:
  - `400 EMPTY_CART`;
  - `422 UNAVAILABLE_ITEMS` (names the items);
  - `400 PICKUP_LOCATION_REQUIRED`;
  - `422 PICKUP_LOCATION_OUT_OF_REGION`;
  - `422 DELIVERY_ADDRESS_REQUIRED`.

  These close the gaps noted in 3.2: unavailable items, stale prices, pickup region and missing address.
- **Idempotency:** the client sends an `Idempotency-Key` header (8–64 letters, digits or dashes); the checkout generates one per visit and reuses it on retries. A repeat returns the original order with **200 and `duplicate: true`** (new orders are 201). A unique constraint on (buyer, key) makes this hold even for simultaneous requests: the losing request returns the winner's order. This is stronger than the story's 30-second window.
- **Order number (deviation):** order IDs stay UUIDs (switching to ULIDs would change every table that references orders); each order also gets a short unique **order number** such as `CM-7K3F9Q2X` (Crockford base32) shown to buyers and admins. Orders sort by `createdAt`.
- **`GET /orders/{id}`** returns the confirmation: order number, status, payment status, items (unit price, line totals), totals, and the delivery address or pickup point (with hours). Another buyer's order returns **404** (previously 403), so order IDs can't be probed.
- **Admin notification (AC4):** no email service is configured, so a row is written to a new `notifications` table in the same transaction (as the story suggests, ready for a future email/SMS worker) and logged. Admins see them on the dashboard (unread count, mark one or all as read, refreshes every minute) via `GET /admin/notifications`, `POST /admin/notifications/{id}/read` and `/read-all`. `AdminNotifier` plays the role of the `Notifier` util.
- **Frontend:**
  - "Place order" calls the API, reloads the (now empty) cart and goes to `/orders/confirmation?orderId=`. On `EMPTY_CART` or `UNAVAILABLE_ITEMS` it shows the reason and reloads the cart, so checkout shows the matching state. The empty-cart case shows the empty state instead of a disabled button with a tooltip.
  - `/orders/**` is buyer-only (signed-out visitors go to sign in and back).
  - The confirmation shows a thank-you, order number, date, status, "Pay when you receive/collect it", fulfillment details, items and totals.
- **Bug found by E2E:** the Next.js API proxy didn't forward the `Idempotency-Key` header, so duplicate protection silently didn't work through the web app. It now does (with a unit test).
- Payment: orders are `UNPAID` (pay on delivery/collection); online payment is out of scope. Stock is not deducted (deferred, per the constraints).
