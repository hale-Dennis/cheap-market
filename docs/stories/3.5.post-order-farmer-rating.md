## Story
**As a** Buyer,
**I want** to rate the farmer after my order is completed,
**so that** I can share my feedback with the community.

## Acceptance Criteria
1. When an order's status is "Completed," the buyer has an option to rate the farmer(s) from that order.
2. The buyer can submit a 1-5 star rating.
3. The submitted rating is attached to the farmer's profile and contributes to their overall average rating.
4. A buyer can only rate a farmer once per completed order.

## Dev Agent Record

### Implementation Notes
- **One rating per farmer per order.** An order can contain produce from several farmers, so each farmer is rated separately (AC1 "farmer(s)").
  - `POST /ratings` now takes `farmerId` as well as `orderId`, `score` and `comment`.
  - The existing code rated only the first item's farmer, and its unique constraint on `order_id` allowed one rating per order. The table now has a unique constraint on `(order_id, farmer_id)`.
- **Rules:**
  - Another buyer's order returns 404, as `GET /orders/{id}` does.
  - An order that isn't completed returns `422 ORDER_NOT_COMPLETED`.
  - A farmer who didn't supply the order returns `422 FARMER_NOT_IN_ORDER`.
  - A repeat returns `409 ALREADY_RATED`. This also holds for simultaneous requests: the database constraint is caught and mapped to the same 409.
  - A score outside 1–5 returns 400.
- **Farmer average (AC3):**
  - The farmer's row is locked, then `averageRating` (2 decimal places) and `ratingCount` are recomputed from all of their ratings.
  - Concurrent ratings for the same farmer therefore queue rather than overwrite each other. The old incremental update could drift and race.
  - `GET /ratings?farmerId=` is public and returns `{ averageRating, ratingCount }`.
  - The product page is server-rendered, so `FarmerInfo` shows the new average on its next load.
- **Order responses:**
  - `GET /orders/{id}` now lists the order's `farmers`, each with the buyer's rating or `null`.
  - Each `GET /orders` row has `farmersToRate`: farmers in completed orders not yet rated, fetched with one query per page.
- **Frontend:**
  - **`RateFarmerModal`:**
    - 1–5 stars as a radio group, so it works with the keyboard and screen readers. Hovering previews a score, and the choice is described in words ("4 out of 5 · Very good").
    - Submit is disabled until a star is chosen.
    - Optional comment with a `n/300 characters` counter; it can't go over 300, pasted text included.
  - **My orders:** completed orders show a "★ Rate {farmer}" button for each unrated farmer. It sits outside the row link and disappears once the farmer is rated.
  - **Order page:** completed orders get a "Rate your farmer(s)" section showing each rating (stars, "You rated 4 out of 5" and the comment) or a Rate button.
  - **Duplicates:** a 409 shows a toast and refreshes to the existing rating.
  - The `Stars` display moved out of `FarmerInfo` into `components/ratings/Stars.tsx` so both places use it.
- **Deviations:**
  - A comment over 300 characters returns **400** (bean validation), not 422 `COMMENT_TOO_LONG`, following the project decision in 1.5 to keep validation errors at 400. The UI prevents it anyway.
  - The files follow the codebase layout (`components/ratings/`, `services/ratingService.ts`) rather than `components/RateFarmerModal.tsx` and `lib/api/ratings.ts`.
- **Schema fix:** `comment` was `@Lob`, which Postgres stores as a large object (`oid`). It is now `varchar(300)`. Hibernate's `ddl-auto: update` can't change an existing column type or drop the old unique constraint. The local table was empty and has been recreated, and CI starts from a fresh database. **Any other existing database needs the `ratings` table dropped (if empty) or migrated before deploying.**
